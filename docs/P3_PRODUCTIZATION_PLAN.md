# 棋聚 QIJU：P3 產品化功能用途與實作規劃

## 文件目的

本文件把產品化階段（P3）的每個功能拆開說明，回答四個問題：

- 這個功能要解決什麼問題？
- 玩家或營運者會因此得到什麼價值？
- 第一個可交付版本（MVP）需要做到哪裡？
- 它依賴哪些資料、權限與既有模組？

這是一份產品與技術邊界文件，不代表所有功能要在同一個版本一次完成。每個功能都會先以能驗證價值、容易回復與不破壞既有對局為原則，再逐步增加完整度。

## 目前基準與 P3 目標

目前專案已經有以下基礎：

- P0 的 PostgreSQL `RoomStore`、一般棋類 snapshot、重啟恢復、token hash 與 TTL 已完成。
- P1 的日麻 session snapshot／restore 已完成；多實例 Redis 仍保留到需要時再做。
- Docker Compose 已能先執行 migration，再啟動應用程式；映像也可發布至 GHCR。
- 線上對局仍以 guest、房間代碼與重連 token 為主，尚未有正式帳號、好友、對局歷史、積分或排行榜。
- PostgreSQL 目前主要保存進行中的房間狀態，不等於完整的玩家帳號資料庫或永久對局歷史。

P3 的目標，是把「可以玩的一組棋類」提升成「玩家願意重複回來、可以累積紀錄、能公平競爭、也方便營運的產品」。因此 P3 的重點不是只增加棋規，而是補上身份、比賽、留存、可及性與營運能力。

## P3 的產品原則

### 1. 對局公平優先

評分、配對、觀戰與計時都必須由伺服器判定。客戶端可以負責顯示與送出意圖，但不能決定勝負、剩餘時間、隱藏資訊或 rating 結果。

### 2. 不讓新功能破壞現有 guest 流程

正式帳號是增量能力。沒有登入的玩家仍應能建立房間、使用既有 token 重連並遊玩；登入功能成熟後，才逐步把 guest 對局綁定到帳號。

### 3. 先建立可追溯資料，再做社交與商業化

好友、評分、排行榜與個人統計都需要穩定的玩家和對局資料。若只在房間 snapshot 上直接加功能，房間過期後就無法可靠回答「誰在什麼時間與誰完成了哪一局」。

### 4. 付費只提供外觀或服務，不提供勝率

棋盤、棋子、主題、進階分析可以產品化；增加額外思考時間、付費解鎖更強 AI 或影響配對公平的能力，應避免成為付費勝利。

## P3-0：產品化底座

P3-0 是其他 P3 功能共用的資料與權限基礎。它不是直接讓玩家看到的新玩法，但缺少它時，好友、評分、排行榜、觀戰權限與付費物品都會各自建立一套不一致的身份判斷。

### P3-0.1 玩家身份（users / identities）

**用途：** 為玩家建立穩定的產品身份，讓玩家換裝置、換房間或重新登入後，仍能找回自己的歷史與設定。

**要解決的問題：** 目前房間 token 只能證明「可以回到某個房間的某個 seat」，不能代表一個跨對局的玩家。房間過期後，系統也無法把多場對局可靠地歸戶。

**MVP：** 建立 `users` 與身份狀態，至少包含不可變的 `id`、顯示名稱、建立時間、停權狀態與最後活動時間。第一版可以先支援一種登入方式，不要同時引入多家 OAuth 而放大帳號合併問題。

**邊界：** 使用者名稱不是安全認證；顯示名稱可以改，但內部 `userId` 不應改。既有房間 token 仍是房間重連憑證，不應直接當成長期登入憑證。

### P3-0.2 Session 與登入狀態

**用途：** 讓 HTTP API 與 WebSocket 都能知道請求者是誰，並可以撤銷被盜或過期的登入狀態。

**要解決的問題：** 若把 user ID 或原始 token 放進瀏覽器可讀的長期資料，攻擊者拿到後就可能冒用帳號；若只靠 WebSocket 連線，又無法支援個人設定、歷史與好友等 HTTP 功能。

**MVP：** 使用隨機 session token，資料庫只保存 hash、`userId`、建立時間、過期時間與撤銷時間；瀏覽器以 `HttpOnly`、`Secure`、適當 `SameSite` 的 cookie 保存。WebSocket 握手時驗證 session，再把 user identity 綁到連線。

**安全要求：** 登出要能撤銷 session；敏感操作要檢查 CSRF 與來源；log 不得出現原始 session、房間 token、密碼或完整 cookie。guest 模式應有明確的匿名權限，不可因未登入而繞過房間權限。

### P3-0.3 對局生命週期（matches / participants）

**用途：** 將「正在進行的房間」和「已完成、可查詢的比賽」分開保存，支援歷史、評分、統計、重播與申訴。

**要解決的問題：** 房間 snapshot 是恢復當下狀態的技術資料；它不適合直接當成產品歷史。房間可能因 TTL 消失，也可能包含不應長期暴露的日麻暗牌資訊。

**MVP：** 建立 `matches` 與 `match_participants` 概念，記錄 `matchId`、棋種、模式（AI／同機／好友房／rated）、參與者、開始／結束時間、結果、終局原因、schema version 與資料保留狀態。對局從建立、進行中、完成、取消到中止要有明確狀態轉移。

**完成條件：** 只有伺服器確認的合法終局才可寫入完成結果；重連或服務重啟不能產生兩筆相同的完成紀錄；未完成房間仍由現有 `RoomStore` snapshot 負責恢復。

### P3-0.4 最小事件與重播契約

**用途：** 保留足以重建或檢查一局對局的事件，讓未來能做重播、分享、爭議追查、每日挑戰與賽事紀錄。

**MVP：** 一般棋類至少記錄合法走法、ply、伺服器版本與時間；日麻至少記錄公開牌局事件、座位 action 與 schema version，並把暗牌／私有資訊依權限分開。事件格式要有 `eventType`、`sequence`、`matchId`、`createdAt` 與 `schemaVersion`，重複收到同一事件時不能重複套用。

**重要限制：** 第一階段只建立穩定的資料契約，不要求同時完成完整重播 UI、分享網址或每種棋類的分析。這讓 P3 可以先使用對局結果與基本事件，而不必把所有產品功能綁死在尚未成熟的重播格式上。

### P3-0.5 權限、隱私與稽核

**用途：** 定義玩家、對手、觀戰者、賽事管理者與系統管理者各自能讀寫什麼，避免「能看到房間」被錯誤擴大成「能看到所有資料」。

**MVP：** 把權限判定集中在 server/application layer，至少區分 owner、participant、spectator、admin；歷史查詢只能讀取自己的資料或明確公開的比賽；日麻觀戰永遠不能取得其他座位的暗牌。

**稽核內容：** 記錄登入失敗、權限拒絕、評分結果變更、管理員處置與對局中止等重要操作，但只保存必要的 request／match／user 識別資訊，不保存密碼、原始 token 或未授權的隱藏手牌。

### P3-0.6 產品化底座的驗收標準

完成 P3-0 的最低標準是：

- 既有未登入玩家仍可使用房間代碼與重連 token 完成一般對局。
- 登入後建立的對局可以唯一關聯到玩家與對手，不因房間 TTL 消失而消失。
- session 可過期、登出與撤銷，資料庫不保存原始 token。
- 伺服器重啟或重送訊息不會重複結算同一局。
- 查詢歷史時不會把日麻暗牌或其他玩家的私有資料送給不具權限的客戶端。
- schema 變更可透過現有 migration 流程部署與回滾，並有資料保留策略。

## P3-1：帳號、社交、歷史與評分

P3-1 的重點，是把一次性的房間遊戲變成可以累積關係與成績的服務。這一區塊應建立在 P3-0 的 user、session、match 與權限模型上；不要直接從前端顯示名稱或房間 token 推導好友、排名與勝負。

### P3-1.1 Guest 升級為正式帳號

**用途：** 讓玩家先快速開始遊戲，之後再把身份升級成可跨裝置登入的正式帳號，降低第一次使用時的註冊阻力。

**玩家價值：** 玩家不必在第一次開啟網站時填寫完整資料，但登入後可以保留名稱、設定、對局歷史、好友與評分。

**MVP：** 為匿名 guest 建立臨時 identity；登入或註冊成功後，將尚未結算且符合規則的 guest 對局綁定至正式 `userId`。若 guest 在多個裝置或不同瀏覽器同時存在，必須明確要求玩家選擇要合併的帳號，不能依顯示名稱自動合併。

**資料邊界：** 已完成的舊 guest 對局是否可補綁，要由產品規則明確決定；第一版可只保證「升級後新建立的對局」一定歸戶，避免猜測歷史所有權。

### P3-1.2 個人資料與偏好

**用途：** 保存玩家在不同對局間共用的顯示名稱、頭像識別、語言、主題、音效與隱私設定。

**MVP：** 提供顯示名稱修改、帳號停用、公開／不公開歷史、是否允許好友邀請與是否顯示線上狀態。名稱要有長度、字元與冒犯內容限制，並以 user ID 而不是名稱做關聯。

**為什麼需要獨立做：** 偏好設定屬於 user profile，不應塞進房間 snapshot；否則清除房間或換棋種時會遺失，也無法在登入前端一致套用。

### P3-1.3 好友與邀請

**用途：** 讓玩家可以重複找到熟人，直接邀請進入指定棋種或房間，而不必每次複製房間代碼。

**MVP：** 支援以 user ID 或唯一名稱搜尋、送出／接受／拒絕／取消好友邀請、移除好友與封鎖玩家。好友清單先提供「可邀請」狀態；即時線上狀態可在資料模型穩定後再加，不應把 presence 當成好友功能的必要條件。

**權限與隱私：** 被封鎖的玩家不能送邀請、加入私人房或透過配對反覆騷擾；拒絕邀請後應有冷卻時間。公開顯示的資料只需要名稱、頭像與必要的線上狀態，不公開 email、session 或連線資訊。

### P3-1.4 私人邀請與房間銜接

**用途：** 把好友關係接到現有房間協定，讓邀請可以直接開啟正確的棋種、模式與 seat，而不是只傳一個沒有上下文的 URL。

**MVP：** 產生短期、一次性或可撤銷的邀請；邀請內只放 opaque invite ID，不放房間 token。伺服器驗證邀請者、受邀者、房間狀態與有效期限後，才發給接收者自己的 seat token。

**不可混用的概念：** 好友邀請是社交關係操作，房間邀請是進入特定對局的授權；兩者不可共用同一個長期 token，也不可因「是好友」就直接取得對局內的所有權限。

### P3-1.5 對局歷史

**用途：** 讓玩家知道自己玩過什麼、輸贏如何、對手是誰，並作為重播、統計、申訴與排行榜的入口。

**MVP：** 提供自己的歷史列表，支援依棋種、模式、日期與結果篩選；每筆至少顯示棋種、對手或 AI、結果、終局原因、開始／結束時間與是否 rated。列表 API 必須分頁，不應一次回傳整個帳號的所有紀錄。

**延伸：** 點入單局後可查看公開對局資訊與事件摘要；完整逐手重播、分享連結、日麻牌譜與隱藏資訊控制依 P3-0 的 event schema 逐步加入。歷史資料要有保留與刪除政策，帳號停用時不能無限期保留可識別個資。

### P3-1.6 Rated 對局與 ELO／Glicko

**用途：** 用可理解的分數描述玩家在特定棋種與模式的相對實力，讓配對更公平，也提供持續進步的目標。

**MVP：** 第一版可從每個棋種各自的 ELO 開始：完成一場 rated 對局後，由伺服器依賽前分數、結果與 K factor 計算新分數。新玩家標記為 provisional，前幾場允許較大幅度變化；AI、同機、取消與非 rated 私人房不得影響分數。

**何時用 Glicko：** 當玩家數量、長時間未對局與不確定性變得重要，再把模型升級為 Glicko-2。模型更換要保存 rating version，並提供離線重算或遷移工具，不能因部署版本不同而讓同一場比賽被計算兩次。

**反作弊與爭議：** 評分只接受 server authoritative 的完成結果；斷線、超時、投降與管理員判定要有一致規則。短時間重複對戰、異常勝率、同一裝置大量帳號等訊號可先記錄供檢查，第一版不必直接用黑箱模型封鎖玩家。

### P3-1.7 排行榜與賽季

**用途：** 把 rating 變成可探索的競爭目標，讓玩家知道自己的位置與近期進步，而不只看到一個孤立分數。

**MVP：** 依棋種與 rating mode 提供前 N 名、玩家自己的名次、分數、勝場與賽季期間；支援分頁與並列名次。排行榜讀取應使用預先計算或可索引的查詢，不能每次載入都掃描所有對局事件。

**賽季規則：** 明確定義開始／結束時間、是否重置 rating、最低完成場數、停權帳號如何處理與歷史賽季是否保留。排行榜是公開資料，但玩家可選擇隱藏顯示名稱；隱藏後仍需保留內部統計與管理稽核資料。

### P3-1.8 P3-1 的驗收標準

完成 P3-1 的最低標準是：

- 玩家可從 guest 升級帳號，且既有房間重連 token 不會因此失效。
- 好友、封鎖與私人邀請的權限在伺服器判定，不可只依前端按鈕狀態信任。
- 玩家只能查到自己的非公開歷史；公開對局也不會洩漏日麻私有資訊。
- rated 對局只在唯一且合法的終局事件後結算一次，重試請求不會重複加分。
- rating、排行榜與 match history 都能由同一個 `matchId` 追溯到參與者與結果。
- 刪除、停用、封鎖與管理員處置都有明確的資料保留和稽核規則。
