# 棋聚 QIJU：P3 產品化功能用途與實作規劃

## 文件目的

本文件把產品化階段（P3）的每個功能拆開說明，回答四個問題：

- 這個功能要解決什麼問題？
- 玩家或營運者會因此得到什麼價值？
- 第一個可交付版本（MVP）需要做到哪裡？
- 它依賴哪些資料、權限與既有模組？

這是一份產品與技術邊界文件，不代表所有功能要在同一個版本一次完成。每個功能都會先以能驗證價值、容易回復與不破壞既有對局為原則，再逐步增加完整度。

## 目前基準與 P3 目標

目前專案已經有以下基礎：

- P0 的 PostgreSQL `RoomStore`、一般棋類 snapshot、重啟恢復、token hash 與 TTL 已完成。
- P1 的日麻 session snapshot／restore 已完成；多實例 Redis 仍保留到需要時再做。
- Docker Compose 已能先執行 migration，再啟動應用程式；映像也可發布至 GHCR。
- P3-A／P3-B 已補上 guest session、自己的對局歷史 API、個人偏好與基本統計；正式帳號合併、好友、積分與排行榜仍未開始。
- 對戰聊天室與 emoji 已納入 P3-C／P3-E 規劃；P3-C 已完成聊天室、rated／ELO 與公開配對第一個切片，先支援對局玩家聊天、兩人一般棋類競技私人房與公開配對，觀戰聊天室仍未開始。
- PostgreSQL 現在同時保存進行中的房間、產品化 match／事件與個人偏好，但仍不等於完整的社交與競技資料庫。

P3 的目標，是把「可以玩的一組棋類」提升成「玩家願意重複回來、可以累積紀錄、能公平競爭、也方便營運的產品」。因此 P3 的重點不是只增加棋規，而是補上身份、比賽、留存、可及性與營運能力。

## P3 的產品原則

### 1. 對局公平優先

評分、配對、觀戰與計時都必須由伺服器判定。客戶端可以負責顯示與送出意圖，但不能決定勝負、剩餘時間、隱藏資訊或 rating 結果。

### 2. 不讓新功能破壞現有 guest 流程

正式帳號是增量能力。沒有登入的玩家仍應能建立房間、使用既有 token 重連並遊玩；登入功能成熟後，才逐步把 guest 對局綁定到帳號。

### 3. 先建立可追溯資料，再做社交與商業化

好友、評分、排行榜與個人統計都需要穩定的玩家和對局資料。若只在房間 snapshot 上直接加功能，房間過期後就無法可靠回答「誰在什麼時間與誰完成了哪一局」。

### 4. 付費只提供外觀或服務，不提供勝率

棋盤、棋子、主題、進階分析可以產品化；增加額外思考時間、付費解鎖更強 AI 或影響配對公平的能力，應避免成為付費勝利。

## P3-0：產品化底座

P3-0 是其他 P3 功能共用的資料與權限基礎。它不是直接讓玩家看到的新玩法，但缺少它時，好友、評分、排行榜、觀戰權限與付費物品都會各自建立一套不一致的身份判斷。

### P3-0.1 玩家身份（users / identities）

**用途：** 為玩家建立穩定的產品身份，讓玩家換裝置、換房間或重新登入後，仍能找回自己的歷史與設定。

**要解決的問題：** 目前房間 token 只能證明「可以回到某個房間的某個 seat」，不能代表一個跨對局的玩家。房間過期後，系統也無法把多場對局可靠地歸戶。

**MVP：** 建立 `users` 與身份狀態，至少包含不可變的 `id`、顯示名稱、建立時間、停權狀態與最後活動時間。第一版可以先支援一種登入方式，不要同時引入多家 OAuth 而放大帳號合併問題。

**邊界：** 使用者名稱不是安全認證；顯示名稱可以改，但內部 `userId` 不應改。既有房間 token 仍是房間重連憑證，不應直接當成長期登入憑證。

### P3-0.2 Session 與登入狀態

**用途：** 讓 HTTP API 與 WebSocket 都能知道請求者是誰，並可以撤銷被盜或過期的登入狀態。

**要解決的問題：** 若把 user ID 或原始 token 放進瀏覽器可讀的長期資料，攻擊者拿到後就可能冒用帳號；若只靠 WebSocket 連線，又無法支援個人設定、歷史與好友等 HTTP 功能。

**MVP：** 使用隨機 session token，資料庫只保存 hash、`userId`、建立時間、過期時間與撤銷時間；瀏覽器以 `HttpOnly`、`Secure`、適當 `SameSite` 的 cookie 保存。WebSocket 握手時驗證 session，再把 user identity 綁到連線。

**安全要求：** 登出要能撤銷 session；敏感操作要檢查 CSRF 與來源；log 不得出現原始 session、房間 token、密碼或完整 cookie。guest 模式應有明確的匿名權限，不可因未登入而繞過房間權限。

### P3-0.3 對局生命週期（matches / participants）

**用途：** 將「正在進行的房間」和「已完成、可查詢的比賽」分開保存，支援歷史、評分、統計、重播與申訴。

**要解決的問題：** 房間 snapshot 是恢復當下狀態的技術資料；它不適合直接當成產品歷史。房間可能因 TTL 消失，也可能包含不應長期暴露的日麻暗牌資訊。

**MVP：** 建立 `matches` 與 `match_participants` 概念，記錄 `matchId`、棋種、模式（AI／同機／好友房／rated）、參與者、開始／結束時間、結果、終局原因、schema version 與資料保留狀態。對局從建立、進行中、完成、取消到中止要有明確狀態轉移。

**完成條件：** 只有伺服器確認的合法終局才可寫入完成結果；重連或服務重啟不能產生兩筆相同的完成紀錄；未完成房間仍由現有 `RoomStore` snapshot 負責恢復。

### P3-0.4 最小事件與重播契約

**用途：** 保留足以重建或檢查一局對局的事件，讓未來能做重播、分享、爭議追查、每日挑戰與賽事紀錄。

**MVP：** 一般棋類至少記錄合法走法、ply、伺服器版本與時間；日麻至少記錄公開牌局事件、座位 action 與 schema version，並把暗牌／私有資訊依權限分開。事件格式要有 `eventType`、`sequence`、`matchId`、`createdAt` 與 `schemaVersion`，重複收到同一事件時不能重複套用。

**重要限制：** 第一階段只建立穩定的資料契約，不要求同時完成完整重播 UI、分享網址或每種棋類的分析。這讓 P3 可以先使用對局結果與基本事件，而不必把所有產品功能綁死在尚未成熟的重播格式上。

### P3-0.5 權限、隱私與稽核

**用途：** 定義玩家、對手、觀戰者、賽事管理者與系統管理者各自能讀寫什麼，避免「能看到房間」被錯誤擴大成「能看到所有資料」。

**MVP：** 把權限判定集中在 server/application layer，至少區分 owner、participant、spectator、admin；歷史查詢只能讀取自己的資料或明確公開的比賽；日麻觀戰永遠不能取得其他座位的暗牌。

**稽核內容：** 記錄登入失敗、權限拒絕、評分結果變更、管理員處置與對局中止等重要操作，但只保存必要的 request／match／user 識別資訊，不保存密碼、原始 token 或未授權的隱藏手牌。

### P3-0.6 產品化底座的驗收標準

完成 P3-0 的最低標準是：

- 既有未登入玩家仍可使用房間代碼與重連 token 完成一般對局。
- 登入後建立的對局可以唯一關聯到玩家與對手，不因房間 TTL 消失而消失。
- session 可過期、登出與撤銷，資料庫不保存原始 token。
- 伺服器重啟或重送訊息不會重複結算同一局。
- 查詢歷史時不會把日麻暗牌或其他玩家的私有資料送給不具權限的客戶端。
- schema 變更可透過現有 migration 流程部署與回滾，並有資料保留策略。

## P3-1：帳號、社交、歷史與評分

P3-1 的重點，是把一次性的房間遊戲變成可以累積關係與成績的服務。這一區塊應建立在 P3-0 的 user、session、match 與權限模型上；不要直接從前端顯示名稱或房間 token 推導好友、排名與勝負。

### P3-1.1 Guest 升級為正式帳號

**用途：** 讓玩家先快速開始遊戲，之後再把身份升級成可跨裝置登入的正式帳號，降低第一次使用時的註冊阻力。

**玩家價值：** 玩家不必在第一次開啟網站時填寫完整資料，但登入後可以保留名稱、設定、對局歷史、好友與評分。

**MVP：** 為匿名 guest 建立臨時 identity；登入或註冊成功後，將尚未結算且符合規則的 guest 對局綁定至正式 `userId`。若 guest 在多個裝置或不同瀏覽器同時存在，必須明確要求玩家選擇要合併的帳號，不能依顯示名稱自動合併。

**資料邊界：** 已完成的舊 guest 對局是否可補綁，要由產品規則明確決定；第一版可只保證「升級後新建立的對局」一定歸戶，避免猜測歷史所有權。

### P3-1.2 個人資料與偏好

**用途：** 保存玩家在不同對局間共用的顯示名稱、頭像識別、語言、主題、音效與隱私設定。

**MVP：** 提供顯示名稱修改、帳號停用、公開／不公開歷史、是否允許好友邀請與是否顯示線上狀態。名稱要有長度、字元與冒犯內容限制，並以 user ID 而不是名稱做關聯。

**為什麼需要獨立做：** 偏好設定屬於 user profile，不應塞進房間 snapshot；否則清除房間或換棋種時會遺失，也無法在登入前端一致套用。

### P3-1.3 好友與邀請

**用途：** 讓玩家可以重複找到熟人，直接邀請進入指定棋種或房間，而不必每次複製房間代碼。

**MVP：** 支援以 user ID 或唯一名稱搜尋、送出／接受／拒絕／取消好友邀請、移除好友與封鎖玩家。好友清單先提供「可邀請」狀態；即時線上狀態可在資料模型穩定後再加，不應把 presence 當成好友功能的必要條件。

**權限與隱私：** 被封鎖的玩家不能送邀請、加入私人房或透過配對反覆騷擾；拒絕邀請後應有冷卻時間。公開顯示的資料只需要名稱、頭像與必要的線上狀態，不公開 email、session 或連線資訊。

### P3-1.4 私人邀請與房間銜接

**用途：** 把好友關係接到現有房間協定，讓邀請可以直接開啟正確的棋種、模式與 seat，而不是只傳一個沒有上下文的 URL。

**MVP：** 產生短期、一次性或可撤銷的邀請；邀請內只放 opaque invite ID，不放房間 token。伺服器驗證邀請者、受邀者、房間狀態與有效期限後，才發給接收者自己的 seat token。

**不可混用的概念：** 好友邀請是社交關係操作，房間邀請是進入特定對局的授權；兩者不可共用同一個長期 token，也不可因「是好友」就直接取得對局內的所有權限。

### P3-1.5 對局歷史

**用途：** 讓玩家知道自己玩過什麼、輸贏如何、對手是誰，並作為重播、統計、申訴與排行榜的入口。

**MVP：** 提供自己的歷史列表，支援依棋種、模式、日期與結果篩選；每筆至少顯示棋種、對手或 AI、結果、終局原因、開始／結束時間與是否 rated。列表 API 必須分頁，不應一次回傳整個帳號的所有紀錄。

**延伸：** 點入單局後可查看公開對局資訊與事件摘要；完整逐手重播、分享連結、日麻牌譜與隱藏資訊控制依 P3-0 的 event schema 逐步加入。歷史資料要有保留與刪除政策，帳號停用時不能無限期保留可識別個資。

### P3-1.6 Rated 對局與 ELO／Glicko

**用途：** 用可理解的分數描述玩家在特定棋種與模式的相對實力，讓配對更公平，也提供持續進步的目標。

**MVP：** 第一版可從每個棋種各自的 ELO 開始：完成一場 rated 對局後，由伺服器依賽前分數、結果與 K factor 計算新分數。新玩家標記為 provisional，前幾場允許較大幅度變化；AI、同機、取消與非 rated 私人房不得影響分數。

**何時用 Glicko：** 當玩家數量、長時間未對局與不確定性變得重要，再把模型升級為 Glicko-2。模型更換要保存 rating version，並提供離線重算或遷移工具，不能因部署版本不同而讓同一場比賽被計算兩次。

**反作弊與爭議：** 評分只接受 server authoritative 的完成結果；斷線、超時、投降與管理員判定要有一致規則。短時間重複對戰、異常勝率、同一裝置大量帳號等訊號可先記錄供檢查，第一版不必直接用黑箱模型封鎖玩家。

### P3-1.7 排行榜與賽季

**用途：** 把 rating 變成可探索的競爭目標，讓玩家知道自己的位置與近期進步，而不只看到一個孤立分數。

**MVP：** 依棋種與 rating mode 提供前 N 名、玩家自己的名次、分數、勝場與賽季期間；支援分頁與並列名次。排行榜讀取應使用預先計算或可索引的查詢，不能每次載入都掃描所有對局事件。

**賽季規則：** 明確定義開始／結束時間、是否重置 rating、最低完成場數、停權帳號如何處理與歷史賽季是否保留。排行榜是公開資料，但玩家可選擇隱藏顯示名稱；隱藏後仍需保留內部統計與管理稽核資料。

### P3-1.8 P3-1 的驗收標準

完成 P3-1 的最低標準是：

- 玩家可從 guest 升級帳號，且既有房間重連 token 不會因此失效。
- 好友、封鎖與私人邀請的權限在伺服器判定，不可只依前端按鈕狀態信任。
- 玩家只能查到自己的非公開歷史；公開對局也不會洩漏日麻私有資訊。
- rated 對局只在唯一且合法的終局事件後結算一次，重試請求不會重複加分。
- rating、排行榜與 match history 都能由同一個 `matchId` 追溯到參與者與結果。
- 刪除、停用、封鎖與管理員處置都有明確的資料保留和稽核規則。

## P3-2：公開配對、對局聊天室、觀戰、賽事與對局時鐘

P3-2 把「知道對手的房間」擴展成「系統幫玩家找到對手、讓玩家安全對話、讓其他人安全觀看，並能在明確規則下完成比賽」。這一區塊最容易影響公平性，因此所有 queue、seat、clock、chat 與觀戰資料都必須由伺服器掌握。

### P3-2.1 公開配對（matchmaking）

**用途：** 讓玩家選擇棋種與模式後直接等待對手，降低分享房間代碼、確認 seat 與手動協調時間的成本。

**MVP：** 先支援兩人一般棋類的公開配對，配對條件至少包含棋種、rated／unrated、時間控制與玩家目前的 rating range。玩家加入 queue 後取得 queue ticket；成功配對時由伺服器原子地建立 match 與兩個 participant，並分別發出 seat token。

**取消與斷線：** 玩家可取消尚未配對的 ticket；ticket 要有 TTL，重複加入不應形成多個有效等待項目。配對成功後即使其中一人尚未完成 WebSocket 連線，也要由 match lifecycle 決定是等待、判負、重新配對或取消，不能靠前端猜測。

**日麻限制：** 日麻需要四個座位、局數與東南場規則，不能直接套用兩人棋類 queue。第一版應把日麻當成獨立的四人配對規則，明確處理缺席座位、AI 補位、斷線與私有資訊，不要為了共用 UI 而犧牲 session 的權威性。

### P3-2.2 配對公平與防濫用

**用途：** 避免公開配對變成高分玩家反覆虐新手、帳號刷分或用大量連線佔住資源。

**MVP：** 使用 rating range、等待時間逐步放寬的配對策略；同一帳號不能同時進入互斥的多個 rated queue；配對前檢查封鎖、停權、冷卻與遊戲中的狀態。配對結果要記錄規則版本，之後才能分析失敗率與等待時間。

**不在第一版的項目：** 不先做複雜的跨棋種總分、隱藏 MMR 或機器學習配對。先把「條件可解釋、結果可追溯、取消可恢復」做好，才有資料評估是否需要更複雜的模型。

### P3-2.3 唯讀觀戰模式

**用途：** 讓朋友、社群或賽事觀眾觀看進行中的對局，增加分享性與直播價值，但不給觀戰者影響比賽的權限。

**MVP：** 對公開 match 提供觀戰入口；觀戰連線只能收到伺服器產生的 public view、事件序號與目前比分，不能送出 move、action、seat claim 或 rematch command。觀戰者晚進入時，伺服器要先送目前合法的 snapshot，再依序補送之後的事件。

**隱藏資訊規則：** 一般棋類可顯示完整公開棋盤；日麻只能顯示牌桌公開資訊、河牌、鳴牌與符合觀戰規則的牌面，絕不能把任一座位的手牌、山牌或 server-only random seed 放進觀戰 payload。若未來提供「玩家視角觀戰」，也要針對每個 seat 另外產生權限過濾後的 view。

**容量與安全：** 設定單局觀戰人數上限、單 IP／帳號連線上限與頻率限制；大量觀戰時可讓觀戰者共用 broadcast channel，但資料來源仍是伺服器的單一 match state。觀戰者不應因此取得好友、歷史或未公開房間的查詢權限。

### P3-2.4 賽事房間與小型淘汰賽

**用途：** 讓玩家不只一局一局配對，而能參加有賽程、輪次與晉級結果的活動。

**MVP：** 先支援管理者建立私人賽事、設定棋種／人數／時間控制、產生參賽名單、分配第一輪房間、收集伺服器確認的結果，再由管理者或明確規則產生下一輪。第一版可限制單淘汰、固定人數與人工開始輪次，避免一開始就做完整 Swiss pairing。

**賽事資料：** 需要 `tournament`、`round`、`fixture` 與 match 的關聯；match 結果只能由 fixture 接受，不能讓參賽者自行修改晉級狀態。管理操作要有稽核紀錄，遇到棄權、平手、斷線與爭議時要能暫停 fixture，而不是直接刪除資料。

**日麻賽事：** 日麻不是單純的一對一 bracket。未來若加入，應以場次、順位、總分與座位平衡為核心，另訂 tournament format；不要把一般棋類的勝負晉級模型直接套用。

### P3-2.5 伺服器權威對局時鐘

**用途：** 為棋類與賽事提供可預期的時間壓力，並防止玩家透過修改瀏覽器時間或暫停畫面來作弊。

**MVP：** 在 match 建立時固定 time control，例如每方總時間與 increment；伺服器保存 `turnStartedAt`、剩餘時間與 clock version，每次合法操作都由伺服器計算耗時並更新。瀏覽器只用 server timestamp 做顯示倒數，重新整理或重連後從伺服器 snapshot 重建。

**斷線與暫停：** 規則必須先定義斷線是否繼續扣時、私人房是否允許 host pause、rated 是否禁止人工暫停，以及超時發生在同時收到兩個操作時誰優先。第一版 rated match 建議採伺服器持續計時、斷線不自動暫停；友誼房可以另外提供明確的雙方同意暫停。

**日麻特殊性：** 日麻有摸牌、思考、鳴牌與多家同時反應，不一定只有一個簡單的 current player clock。日麻第一版可先做整場或每巡限制，再依 `RiichiSession` 的 action state 設計座位計時；不可在前端以一般棋類的單一倒數器硬套。

### P3-2.6 對局聊天室與 emoji

**用途：** 讓對戰玩家在等待、落子與結束後可以用文字和 emoji 溝通，增加好友房與公開配對的互動性；聊天室是對局的附屬能力，不得成為下棋指令，也不能影響伺服器對勝負、計時或評分的判定。

**MVP：**

- 私人房與 rated／公開配對的對局參與者可以傳送純文字訊息與 Unicode emoji；前端提供 emoji picker 或常用 emoji 快速按鈕，但伺服器接收的仍是文字內容，不引入圖片、檔案或自訂貼圖上傳。
- 訊息由伺服器依 match、session／user 與 seat 權限廣播，至少帶有 `messageId`、`matchId`、發送者身份或 seat、`createdAt` 與房內序號；guest 不需要先升級正式帳號才能使用。
- 重連時只補送有限數量的最近訊息，避免把整段聊天歷史無限帶回；對局結束後不把聊天內容混入 `match_events`、棋譜或玩家統計。
- 訊息先以純文字處理，前端不得把內容當 HTML、Markdown 或可執行模板渲染；emoji 是 UTF-8 文字的一部分，不另建立會影響棋規的訊息型別。

**資料邊界與保存：** 第一版若只需要對局期間與重連後的短暫顯示，可以使用有上限的 room／match memory buffer。若後續需要檢舉、申訴、跨實例同步或管理稽核，再新增獨立的 `qiju_match_chat_messages`，不要把聊天塞進重播事件表；一列代表一則對局聊天室訊息，至少規劃 `id`、`match_id`、`sender_user_id`、`sender_seat`、`body`、`sequence`、`created_at` 與 `moderation_status`，以 `match_id + sequence` 保證順序唯一並建立對應查詢索引。未來真正建立 migration 時，每張表與每個欄位都必須有 PostgreSQL 原生 table／column comment，並明確定義保留、刪除與匿名化規則。

**目前實作進度（2026-09-22）：** P3-C 的第一個可交付聊天室切片已完成。現有對戰房玩家可以在等待對手、對局中與結束後傳送純文字／Unicode emoji；伺服器只對房內玩家廣播，保留最多 50 則最近訊息，單則最多 500 個 Unicode 字元，單一連線 10 秒最多 8 則。訊息不寫入 match event、不放入 PostgreSQL 歷史，重連時由房間狀態補回有限訊息，重開 rematch 時清空。前端提供安全的純文字訊息顯示與常用 emoji 快速按鈕。

**Rating／ELO 目前實作進度（2026-09-22）：** P3-C 的第二個可交付切片已完成。兩人一般棋類可建立 rated 私人房，建立與重連都要求相同的玩家身份；合法終局後由伺服器以 ELO v1 結算，每種棋種各自維護初始 1500 分、前 10 場 provisional 與較高 K factor。結算寫入 `qiju_ratings` 與不可重複的 `qiju_rating_results`，同一 `matchId` 重試不會重複加分；AI、同機、好友房、取消與中止對局不影響 rating。玩家可透過 `/api/me/ratings` 讀取自己的分數與戰績。

**公開配對目前實作進度（2026-09-22）：** P3-C 的第三個可交付切片已完成。兩人一般棋類可選 rated 或 casual 公開配對，伺服器以記憶體 queue 保存 ticket，依棋種、配對類型與目前唯一支援的 `unlimited` time control 配對；rated 會先以 200 分 rating range 尋找對手，等待時間增加時逐步放寬到 800 分。ticket 有 2 分鐘 TTL，可由玩家取消，WebSocket 斷線也會移除；配對成功後由伺服器建立 `public`／`rated` match、兩個 participant 與各自 seat token。這一版刻意維持單實例記憶體 queue，不先引入 Redis；日麻、觀戰、server clock、跨實例 queue 與複雜時間控制留到後續切片。

**權限與防濫用：**

- 只有該 match 的授權參與者能讀寫私人對話；房間 token、session token、日麻手牌、山牌與其他 server-only 資訊不可出現在訊息或錯誤回應中。
- 公開觀戰者若未來需要聊天，必須使用獨立的 public channel 與明確的可見範圍，不能因能觀戰就取得玩家限定聊天室；觀戰聊天排在 P3-E 的權限設計處理。
- 設定訊息長度、控制字元、發送頻率與連線／帳號配額，例如每則最多 500 個 Unicode 字元並限制短時間連發；至少保留 mute、檢舉與管理員隱藏訊息的擴充邊界。
- 被封鎖、停權、離開 match 或沒有有效 seat 權限的連線不能繼續發送；聊天室斷線或故障時，對局本身仍要照常進行。

**P3-2.6 驗收標準：**

- 授權玩家可以在同一場對局中收發文字與 emoji，訊息順序穩定且不會跨房間廣播。
- 未授權連線不能訂閱、讀取或偽造其他玩家的聊天室訊息；日麻測試確認聊天 payload 不會夾帶暗牌或私有事件。
- 長訊息、HTML／script 內容、控制字元與高頻刷訊息會被拒絕或限流，不會造成 XSS、伺服器崩潰或無限記憶體成長。
- 重連只取得規定數量的最近訊息；對局結束、房間過期或達到保留期限後，聊天室資料會依既定政策清理。
- 聊天室訊息不會改變合法走法、match event sequence、剩餘時間、終局結果或 rating 結算。

### P3-2.7 Presence 與重連體驗

**用途：** 告訴玩家對手是否已連線、誰正在觀戰、比賽是否等待 ready，並讓短暫網路波動不會立即被誤判為棄權。

**MVP：** presence 只表示必要狀態，例如 connected、disconnected、ready、finished 與 lastSeen；狀態以 server heartbeat 為準，並有明確的 stale timeout。重連後先取得目前 match snapshot，再依序恢復未讀事件，不讓瀏覽器只靠本地狀態補棋。

**隱私：** 不對一般玩家公開 IP、裝置資訊或精確活動時間；好友看到的線上狀態應可關閉。presence 不能用來繞過 rated match 的斷線判定，也不能由觀戰者取得 participant 的私人聯絡資訊。

### P3-2.8 P3-2 的驗收標準

完成 P3-2 的最低標準是：

- 公開配對不會產生重複 ticket、雙重 seat 或沒有 participant 的 match。
- 玩家取消、斷線、重連與配對超時都有明確且可重試的狀態轉移。
- 觀戰者只能收到 public view，日麻暗牌與 server-only 資訊經過測試確認不會外洩。
- 觀戰者不能送出改變棋局、座位、評分或賽事晉級的指令。
- 對局聊天室只能被授權玩家使用；訊息內容、emoji、限流、重連補送與保留期限都有可測試的邊界。
- 時鐘由伺服器計算，重新整理、改變本機時間與多開分頁不會增加剩餘時間。
- tournament fixture、match result、rating result 之間可追溯，管理員修正結果會留下 audit record。
- 在單實例與未來多實例部署下，presence、match state 與事件序號的責任邊界清楚。

## P3-3：使用體驗與可及性

P3-3 的目的不是只讓畫面更漂亮，而是讓更多玩家能在不同裝置、網路條件與身體能力下，穩定完成一局棋。這一區塊應以現有 `public/index.html`、`style.css`、前端 state 與 Worker 邊界為基礎，避免為了 UI 效果把權威規則搬回瀏覽器。

### P3-3.1 PWA 與離線體驗

**用途：** 讓玩家可以把棋聚安裝到手機或桌面，縮短再次開啟的時間；在網路不穩時仍能載入介面與進行不需要伺服器的內容。

**MVP：** 加入 web app manifest、合適的 icon、theme color、service worker 與可版本化的 cache strategy。靜態 shell、CSS、規則 bundle 與本機 AI 資源可快取；線上房間、帳號、配對與 rated match 必須明確顯示需要網路，不能假裝離線成功。

**離線遊戲邊界：** 一般棋類對 AI 或同機對戰可以在離線狀態運作；日麻若依賴本機 Worker 且已快取完整資源，才標示為可離線，否則提供清楚的不可用原因。線上對局斷線時只保存待送操作與本地顯示狀態，重新連線後仍以 server snapshot 為準。

**更新策略：** cache key 要包含 build version；有新版本時提示玩家重新載入，不可讓舊版前端長期使用過期的 WebSocket message schema。service worker 不得快取私密 API response、session cookie 或玩家歷史的個人資料。

### P3-3.2 深色模式與視覺主題

**用途：** 在低光環境降低刺眼感，也讓玩家能選擇符合個人偏好的棋盤、棋子與牌桌外觀。

**MVP：** 使用 CSS variables 定義背景、文字、棋盤格、合法走法提示、警告與勝負狀態；支援系統 `prefers-color-scheme`，並允許玩家在設定中選擇 light、dark 或 system。所有互動狀態要在兩種主題通過對比度檢查。

**主題模型：** 棋盤、棋子、牌背與牌桌主題以 versioned asset manifest 描述，UI 只引用合法的 theme ID；不要讓玩家輸入任意 URL 造成外部資源追蹤或載入風險。主題切換不可改變棋子語意、可點擊區域或遊戲規則。

### P3-3.3 音效與走子動畫

**用途：** 讓落子、吃子、將軍、和棋、勝負與日麻操作有即時回饋，減少玩家不確定「按鈕是否成功」的情況。

**MVP：** 為一般棋類與日麻定義有限的事件音效與短動畫，提供總開關、音量控制與 reduced motion 選項。動畫只表現已經由狀態機確認的結果，不可在合法性尚未確認前預先播放會誤導玩家的勝負效果。

**效能與可及性：** 背景分頁、低階手機與 prefers-reduced-motion 時要縮短或停用動畫；聲音不能是唯一的狀態提示，將軍、錯誤、輪到誰與計時警告也要用文字或視覺狀態表達。

### P3-3.4 鍵盤與觸控操作

**用途：** 讓不使用滑鼠的玩家可以完整完成選單、房間、棋盤與日麻 action 操作，也改善手機小螢幕與觸控誤觸。

**MVP：** 所有互動元素有可見 focus；tab 順序符合畫面閱讀順序；棋盤支援方向鍵移動焦點、Enter／Space 選取與 Escape 取消；日麻每個合法 action 有可聚焦的按鈕與清楚名稱。手機棋盤要保留足夠的 touch target，不以 hover 作為唯一提示。

**棋盤操作細節：** 鍵盤焦點要能表達目前選中的起點、目的地、持駒或牌；不能只依賴滑鼠座標。當走法被伺服器拒絕或狀態更新時，焦點要回到合理位置，不得跳到頁面頂端。

### P3-3.5 螢幕閱讀器與可及性語意

**用途：** 讓視覺障礙玩家可以理解棋盤狀態、目前回合、合法操作、錯誤與終局結果。

**MVP：** 使用語意化 landmark、heading、button、dialog 與 form label；棋盤格有穩定的座標與棋子名稱；輪到誰、操作成功、操作失敗、重新連線與比賽結束透過 live region 宣告。顏色不能是區分玩家、將軍或合法走法的唯一方式。

**日麻特別處理：** 暗牌必須以「自己的第幾張手牌」等可理解且不洩漏他人資訊的名稱提供；公開牌河、鳴牌、分數與可用 action 分開分組。觀戰、玩家視角與自己的手牌要使用不同的 accessibility tree 邊界。

**測試：** 第一版至少以鍵盤完成主要流程，搭配瀏覽器 accessibility tree 與一種主流螢幕閱讀器檢查；未來再加入自動化 axe／Playwright 檢查，避免只測 HTML 是否存在 aria 屬性。

### P3-3.6 國際化（i18n）

**用途：** 讓棋種名稱、操作提示、錯誤、規則說明、日期與分數可以支援不同語言，而不是在程式中散落硬編碼字串。

**MVP：** 先整理繁體中文 message catalog，建立穩定的 message key、插值規則與 fallback；再加入英文。日期、時間、數字與 rating 使用 locale formatter，棋譜與棋種術語保留明確的 domain glossary。

**實作要求：** 不用字串相加拼接完整句子；複數、性別或數量變化使用可翻譯的 message pattern；API 傳回穩定 error code，由前端依 locale 顯示文字。語言切換後，頁面文字、按鈕、live region、頁面 title 與 PWA manifest 都要一致。

### P3-3.7 P3-3 的驗收標準

完成 P3-3 的最低標準是：

- PWA 可安裝、可版本更新；離線時只允許已明確支援的本機功能，線上對局不會假裝成功。
- light／dark 主題的文字與互動狀態具有足夠對比，且主題切換不改變棋規。
- 音效與動畫可關閉、可降低動態，並且不會取代文字或視覺提示。
- 主要流程可只用鍵盤完成，焦點不會被棋盤 render 或 WebSocket 更新任意吃掉。
- 一般棋類與日麻的回合、合法操作、錯誤、暗牌邊界與終局都有可理解的螢幕閱讀器描述。
- 語言文字來自 message catalog；API error code、日期格式與 PWA 資訊不會因語言切換而不一致。

## P3-4：留存與商業化

P3-4 的目的，是讓玩家有持續回訪的理由，並探索可長期維護的收入來源。這一區塊必須先建立在可靠的 match history、事件資料與帳號權限上；如果還不能準確判定一局結果，就不應急著把挑戰、統計或付費分析放到玩家面前。

### P3-4.1 外觀付費（棋盤、棋子、牌桌與音效）

**用途：** 讓玩家用個人偏好裝飾遊戲，提供不影響勝負的收入來源。

**MVP：** 建立商品目錄與 entitlement 概念，商品至少包含 `itemId`、版本、類型、資產 manifest、可用棋種、價格與上下架狀態；購買完成後把權益綁到 `userId`，前端依 server 回傳的 inventory 套用 theme ID。

**公平邊界：** 外觀不能改變棋盤座標、合法走法、資訊可見性、計時、AI 強度或配對條件。所有玩家都要有可用的預設主題；付費資產載入失敗時回退到內建資產，不可因此不能進入對局。

**安全與營運：** 價格與是否擁有商品以支付平台／伺服器紀錄為準，不能信任客戶端傳來的「已購買」。商品目錄需可下架、退款或撤銷；資產要有版本與授權紀錄，避免只在前端藏一個未使用的 URL。

### P3-4.2 進階 AI 分析

**用途：** 在對局結束後協助玩家理解失誤、比較候選走法與練習，而不是只顯示勝負。

**MVP：** 先針對一般棋類提供非即時的 post-game analysis：選擇一局已完成的 match，伺服器或受控 Worker 依固定深度／時間產生關鍵局面、候選走法與簡短說明。結果要保存 engine version、analysis depth、計算時間與 schema version，讓相同對局可重算。

**棋種邊界：** 西洋棋、象棋、將棋、圍棋等可依各自規則與評估器設計；日麻的分析應以牌效率、押／降、打點與局況解釋為主，不能把一般棋類的 minimax 分數直接套用。只有 server 或明確授權的 Worker 可執行分析，不能讓客戶端提交任意結果偽造報告。

**成本控制：** 分析可能是最昂貴的功能之一。第一版應限制每位玩家的每日額度、單局最大計算時間與佇列並發數；免費層提供基本摘要，付費層可增加深度或保存報告，但不應在正在進行的 rated match 中提供會破壞公平的即時提示。

### P3-4.3 個人統計頁

**用途：** 把歷史紀錄轉成玩家看得懂的進步軌跡，例如各棋種勝率、rated 分數變化、平均對局時間與常見終局原因。

**MVP：** 依 `userId` 與棋種聚合已完成的 match，顯示總場數、勝／負／和、rated／unrated 分布、近期表現與 rating trend。查詢要指定時間範圍，並把統計資料與原始 match 分開，避免每次開頁都重掃所有事件。

**解讀邊界：** 小樣本要標示樣本數，不把低於最低場數的勝率包裝成穩定能力；AI 對局、同機對局與 rated 對局分開統計。玩家可隱藏公開個人頁，但自己的私有統計仍可保留供產品功能使用，並提供資料匯出／刪除政策。

### P3-4.4 每日挑戰

**用途：** 提供短時間、固定目標的回訪內容，讓玩家即使沒有對手也能每天完成一個棋類任務。

**MVP：** 由伺服器以日期與 challenge ID 固定題目，題目包含棋種、初始狀態、目標、合法答案與評分規則；玩家提交後由 authoritative rule engine 驗證，完成紀錄以 `userId + challengeId` 做唯一鍵，避免重複領取。

**題目形式：** 一般棋類可使用將死、找最佳手或特定局面；日麻可做牌效率、役種判斷或局況選擇，但必須把可公開資訊與答案邊界定義清楚。第一版可先做一般棋類題目，日麻題庫另外設計。

**獎勵規則：** 獎勵先以徽章、統計或非競技外觀為主；若加入 rating，不應把每日挑戰與正式 rated match 混在一起。題目內容、答案與解析在提交前不可完整送到瀏覽器，避免直接從 network 取得解答。

### P3-4.5 賽季與成就

**用途：** 將每日活動、排行榜與玩家目標組織成有限期間的賽季，提供回訪節奏與長期成就感。

**MVP：** 定義賽季開始／結束、任務、完成條件、獎勵與結算；以不可變的 season version 保存規則。成就應由伺服器依 match、challenge 或社交事件授予，重複事件不應重複發獎。

**公平與隱私：** 賽季任務不可要求玩家購買商品才可完成；排行榜、徽章與公開個人頁要尊重隱私設定。賽季結束後保留歷史結果與獎勵來源，讓客服能處理補發、退款或異常。

### P3-4.6 主題收藏與 inventory

**用途：** 把 P3-3 的主題系統變成可管理的收藏，讓玩家知道擁有哪些物品、目前使用哪個主題，以及不同棋種支援哪些外觀。

**MVP：** 提供 inventory API、裝備／卸下、資產相容性檢查與預設回退。裝備操作要是 user-scoped 且可重複執行；瀏覽器只提交 item ID，伺服器再次檢查 entitlement 與 theme manifest。

**未來擴充：** 可加入主題套組、季節限定、免費試用與活動贈品，但商品狀態、有效期間與撤銷都要由 server 控制。不要把每個 UI 元件都做成可購買物，避免產品複雜度超過玩家能理解的範圍。

### P3-4.7 P3-4 的驗收標準

完成 P3-4 的最低標準是：

- 未付費玩家仍可完整進行核心棋局，付費項目不改變勝率、合法性、資訊或配對公平。
- 商品、inventory、每日挑戰獎勵與分析額度都由伺服器驗證，重送請求不會重複授予權益。
- 外觀資產有版本、授權與回退方案，載入失敗不會阻止玩家進入遊戲。
- AI 分析有 engine version、資源上限、配額與隱私邊界，不能在 rated 對局中提供即時作弊優勢。
- 個人統計能區分棋種、模式與樣本數，且玩家能控制公開程度。
- 每日挑戰、賽季與成就由固定規則產生，完成與獎勵可由事件和 audit record 追溯。

## P3-5：營運、可靠性與未來擴充

P3-5 讓產品功能在真實流量、錯誤與部署變更下仍可被維護。它不一定直接出現在玩家畫面，但會決定出問題時能不能定位、資料能不能恢復，以及何時有足夠理由從單實例擴展成多實例。

### P3-5.1 結構化 log 與資料遮罩

**用途：** 讓開發與營運能依時間、服務、request、room、match 或 user 追查問題，而不是只能閱讀無法搜尋的文字。

**MVP：** 所有 server log 使用 JSON 或固定欄位格式，至少包含時間、level、service、environment、request ID 與 release version；對局相關錯誤再加 room／match ID。現有時間戳與 rotation 設定要延伸到 migration、WebSocket、AI job 與管理操作。

**禁止內容：** 原始 session、房間 token、密碼、cookie、日麻暗牌、隨機 seed 與完整支付資料不可進 log。錯誤物件要先經過 redact；第三方錯誤追蹤也使用同一套遮罩規則。

### P3-5.2 Metrics、health check 與 readiness

**用途：** 分辨「程序活著」與「真的能接新流量」，並用數據知道玩家是否遇到延遲、斷線或資料庫壅塞。

**MVP：** 暴露 liveness 與 readiness；readiness 至少檢查必要的 PostgreSQL 連線與 migration 狀態。記錄低 cardinality 的 metrics，例如 active rooms、WebSocket connections、matchmaking queue size、move latency、reconnect count、DB pool 使用量、migration failure 與 error rate。

**設計原則：** 不把 room ID、user ID、session ID 或任意 URL 當成 metrics label，避免高基數拖垮監控系統。重要的 player-facing 錯誤要有 request ID，讓客服能從畫面回報到 server log。

### P3-5.3 錯誤追蹤與告警

**用途：** 將未處理例外、WebSocket 協定錯誤、資料庫故障與前端 render 問題聚合，讓團隊優先修復真正影響玩家的問題。

**MVP：** 為 server、browser 與 Worker 定義 release version；錯誤事件包含 stack、操作類型、棋種、match mode 與 request ID，但不帶私密 payload。對資料庫連線耗盡、migration 失敗、錯誤率升高、重連率異常與 queue 等待過久設定告警門檻。

**告警規則：** 告警要有 runbook、負責人與降噪方式；不是每個玩家操作錯誤都發 page alert。可以先以 log／metrics 為主，等資料量足夠再導入完整第三方 error tracking。

### P3-5.4 API、WebSocket 與房間限流

**用途：** 防止惡意或失控客戶端耗盡連線、資料庫、AI 計算與 broadcast 資源，保護正常玩家。

**MVP：** 分別限制 IP、user、room 與 connection 的建立頻率；限制 WebSocket message size、每秒訊息數、單房間觀戰人數與 matchmaking ticket 數。建立房間、登入、好友邀請、AI 分析、每日挑戰提交與管理 API 使用不同的 quota。

**錯誤回應：** 被限流時回傳穩定 error code、retry-after 與 request ID；不要讓前端無限重試。限流的 key 不可只用 IP，否則共享網路會誤傷多人；也不可只用 user，否則匿名流量可繞過。

### P3-5.5 PostgreSQL 備份與恢復演練

**用途：** 確保帳號、完成對局、rating、inventory 與賽事資料在資料庫故障或誤操作後可以恢復。

**MVP：** 定義 backup frequency、保留期限、加密位置與誰能執行 restore；至少定期測試能在隔離環境還原 migration 後的 schema 與代表性資料。把 RTO（恢復時間目標）與 RPO（可接受資料遺失量）寫入部署文件。

**資料分層：** 進行中房間 snapshot 可依 TTL 清理；已完成 match、rating 與購買權益需要較長保留。backup 不等於 event replay，恢復資料庫後仍要確認 `sequence`、唯一鍵與 idempotency 不會造成重複結算。

### P3-5.6 Redis 與多實例部署

**用途：** 當單一 Node.js process 無法承受連線或需要多台應用程式時，提供跨實例的 ephemeral coordination，例如 presence、matchmaking queue、pub/sub 與分散式鎖。

**何時才做：** 目前單實例＋PostgreSQL 足以支撐時，不因「未來可能需要」提前增加 Redis 故障面。出現多實例部署、WebSocket 連線分散、queue 需要跨節點或 broadcast 延遲明顯時，才以實際 metrics 啟動這項工作。

**責任分界：** PostgreSQL 仍是帳號、match 結果、rating、inventory 與需要恢復的資料之 source of truth；Redis 只保存可重建的 queue、presence、短期 lock 或 pub/sub。Redis 遺失時不能讓已完成對局消失或重新結算。

**MVP：** 先引入 adapter，例如 `PresenceStore`、`MatchmakingStore` 與 `EventBus`，單實例可使用記憶體實作，Redis 是另一個實作。這樣測試與本機開發不必強制依賴 Redis，也避免把 Redis API 散落在 server handler。

### P3-5.7 部署與版本相容

**用途：** 讓 migration、應用程式、前端 bundle 與 WebSocket schema 的更新可以可預期地進行，降低部署造成大規模斷線或資料不相容的風險。

**MVP：** 維持現有 one-shot migration service 與 app service 分離；部署前執行 typecheck、lint、format、build、一般測試與 PostgreSQL integration test。schema 採向前相容的 expand／migrate／contract 節奏，先新增欄位與讀取支援，再移除舊欄位。

**WebSocket 相容：** message schema 帶版本或可辨識的 command；新 server 至少能理解一段相容期間內的舊 client，舊 client 收到未知事件時要安全忽略或顯示重新載入，而不是讓整個連線崩潰。

### P3-5.8 P3-5 的驗收標準

完成 P3-5 的最低標準是：

- 從 log、request ID 與 metrics 可以定位一筆對局或一次 migration 失敗，但不會洩漏 token、密碼或隱藏牌。
- health 與 readiness 能區分程序活著、資料庫可用與 migration 是否完成。
- 主要資源有可觀測的上限與限流，超過限制時不會造成無限重試或整個 server 崩潰。
- PostgreSQL backup 能在隔離環境成功 restore，並有記錄的 RTO／RPO 與演練步驟。
- 引入 Redis 前已有 abstraction；Redis 只承擔可重建的協調資料，PostgreSQL 仍保護正式產品資料。
- migration、前端 bundle 與 WebSocket schema 有相容策略，部署失敗能停止在安全狀態而不是半套資料。

## P3 建議實作順序

P3 可以先開始規劃與實作，但不建議把所有 P3 功能視為同一個大版本。建議使用下面的切片，每一段都能獨立部署、測試與回復。

| 順序 | 交付切片                    | 主要內容                                                                 | 為什麼先／後做                                             |
| ---- | --------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------- |
| P3-A | 身份與對局資料底座          | users、sessions、matches、participants、最小事件、權限、audit            | 沒有穩定身份與完成紀錄，後續功能都會各自猜資料             |
| P3-B | 歷史與基本個人頁            | history API、guest 升級、個人偏好、基本統計                              | 先驗證玩家是否願意累積資料，成本比公開配對低               |
| P3-C | rated、公開配對與對局聊天室 | ELO、rated policy、queue、取消與斷線規則、玩家限定聊天室                 | 需要先有可靠的 match 結果、身份與 WebSocket 權限           |
| P3-D | 體驗與可及性                | PWA、深色模式、鍵盤、螢幕閱讀器、i18n                                    | 可與後端平行，但要以穩定的前端 state 與 message key 為前提 |
| P3-E | 觀戰、計時與賽事            | public view、server clock、spectator、tournament fixture、觀戰聊天室權限 | 需要事件廣播、權限與終局規則成熟                           |
| P3-F | 留存與商業化                | 每日挑戰、賽季、外觀 inventory、AI 分析                                  | 需要歷史資料、成本控制與權益邊界                           |
| P3-G | 多實例與高流量              | Redis adapter、跨節點 presence／queue／event bus                         | 由 metrics 驅動，不以預測流量作為唯一理由                  |

### P3 與 P2 的關係

P3-A 需要「最小可追溯事件契約」，這是從 P2 的 replay／versioned schema 借用的基礎，但不代表要先完成所有 P2 使用者介面。可以先定義並保存一般棋類 move event 與日麻 public event，之後再交付完整 replay viewer、分享連結與匯出檔案。

同樣地，P3 的個人統計需要 P2 的資料聚合觀念；P3 的每日挑戰需要可重現的局面與規則版本；P3 的 AI 分析需要 match snapshot 或 event replay。這些是依賴關係，不是把所有 P2 專案一次搬進 P3 的理由。

### 第一個 P3 implementation slice

最適合先落地的是 P3-A，範圍可以控制在：

1. 新增 `users`、`sessions`、`matches`、`match_participants` 與 `match_events` migration。
2. 定義 `UserStore`、`SessionStore`、`MatchStore` 與事件寫入的 application abstraction；不要讓 HTTP／WebSocket handler 直接散落 SQL。
3. 將一般棋類的正常終局從 active room snapshot 轉成一筆 idempotent match result。
4. 為 guest 保留原本房間流程，再增加 optional user identity，不強制所有現有流程立即登入。
5. 先補 PostgreSQL integration test、重啟／重送測試、權限測試與日麻暗牌隔離測試。

這一片完成後，才開始把 history、rating、matchmaking 與個人頁接上；若底座測試尚未穩定，先不要引入 Redis、支付或複雜賽季邏輯。

### P3-A 目前實作狀態（2026-09-22）

P3-A 的第一個後端切片已落地：

- PostgreSQL migration 新增 users、sessions、matches、match participants、match events 與 audit log；既有房間 snapshot 以 `match_id`／事件序號與產品化資料關聯。
- `UserStore`、`SessionStore`、`MatchStore`、`AuditStore` 已有 memory／PostgreSQL adapter；session 只保存 hash，對局事件與完成結果以 sequence／狀態轉移保持冪等。
- 一般棋類落子、數子、認輸與日麻公開牌局事件會寫入最小事件契約；正常終局與重連／重啟恢復會沿用同一筆 match。
- guest 房間代碼與 seat token 流程維持不變，另提供可注入的 guest identity／session service；既有 seat 權限與日麻暗牌隔離測試仍保留。
- 已補上 memory、真實 PostgreSQL adapter、事件重送、一般棋類／日麻 server restart 與 E2E 驗證。

本切片刻意尚未加入 history API、登入 cookie／WebSocket handshake、公開觀戰或 rating；這些會在 P3-B／P3-C 以現有 user、session、match 與事件契約為基礎接上，避免先把房間 token 當成長期產品身份。

### P3-B 目前實作狀態（2026-09-22）

P3-B 的第一個可用後端切片已完成：

- 線上模式會建立 HttpOnly guest session；WebSocket handshake 會把有效 session 綁到新加入的房間玩家，既有匿名 seat 也可用原本的 room token 透過 `/api/me/claim-room` 明確認領。
- 提供 `/api/me` 個人資料與偏好更新、`/api/me/matches` 分頁歷史查詢、棋種／模式／結果／日期篩選，以及 `/api/me/stats` 基本勝負統計。
- 個人偏好獨立保存於 `qiju_user_preferences`，不混入房間 snapshot；歷史 API 只回傳目前使用者有權查看的對局摘要，不回傳 user ID 或日麻私有事件。
- memory 與 PostgreSQL adapter 都涵蓋偏好、歷史、統計與 participant 綁定；補上 HTTP、WebSocket、guest claim 與真實 PostgreSQL 行為測試。

本切片尚未加入外部登入／正式帳號合併、好友與封鎖、公開歷史頁面、rating 或排行榜；這些仍依序留在 P3-1 後續與 P3-C，避免把 guest session 誤當成完整帳號系統。

## P3 的整體完成定義

P3 不以「所有列出的功能都存在」作為唯一完成條件，而以產品能安全運作作為完成條件：

- 玩家可以保留身份、找回歷史、邀請好友、在對局中安全對話，並在公開規則下找到對手。
- 一般棋類與日麻都維持伺服器權威；rated、觀戰、計時與隱藏資訊有可測試的邊界。
- 玩家不登入也仍能使用既有核心玩法；登入、付費、觀戰與 PWA 都是漸進式能力。
- 付費外觀與分析有清楚的 entitlement、配額、退款／撤銷與不影響公平的規則。
- 所有重要 match、rating、獎勵與管理操作可由事件、版本與 audit record 追溯。
- 服務有 log、metrics、health、限流、備份與恢復流程；多實例只在單實例指標顯示需要時加入。
- 每一個交付切片都有 migration、automated tests、部署說明與可回復方案，而不是只在本機畫面上完成。
